# G016 Nsight Systems offline recovery

Date: 2026-10-09

## Failed live server capture: evidence and cause

- Nsight Systems version: `2025.1.3.140-251335620677v0`, driver 580.178.04. Falcon service used CUDA logical device 0 after `CUDA_VISIBLE_DEVICES=0`; host mapping is V100 UUID `GPU-eaeb0cc6-58aa-8413-bef3-7fb075992189`, PCI `0000:26:00.0`. RTX 2060 is a separate host index 0 / PCI `0000:25:00.0` and was not the workload.
- The failed profiler-launched service was `python -m sglang.launch_server`, PID 3438348 (scheduler/server, local capture host PID namespace 4026531836). It spawned CUDA worker PID 3438632, other children 3438631 and 3438633, and launcher PID 3438331. Nsys live report metadata enumerates all these as process inventory; scheduler PID 3438348 executed GET/model/tokenizer work; CUDA-serving worker PID 3438632 is the expected CUDA executor. The server log confirms this service reached readiness and later GET /model_info and POST /generate 200 OK. PID 3438632's 22.3GB session storage file, unlike the 113MB server and 17MB tokenizer storage files, identifies it as the runaway storage stream.
- Capture invocation recovered from report metadata:
  `nsys profile --output=.../nsys-falcon-c4-live.nsys-rep --force-overwrite=true --trace=cuda,nvtx,osrt --sample=none --cpuctxsw=none --event-sample=none --gpu-metrics-devices=none --cuda-graph-trace=graph:host-only --cuda-event-trace=false --cuda-flush-interval=0 --stop-on-exit=true <service launcher>`.
- Thus collection was immediate and process-tree based; no `--capture-range` was selected, so the entire service lifetime from startup was collected. The graph setting was explicitly graph-level, host-only (not all graph nodes). Sampling, context-switch trace, event sampling and GPU metric sampling were disabled. However, OSRT was included unnecessarily. The duration was not bounded; `--stop-on-exit=true` stops only when the target exits and is not a duration cap. CLI runtime was about 51 minutes before stopping. There was no c4 request during the active Nsys service: server log's successful test traffic ended ~08:33:11, while the Nsys service became ready ~08:40:24 and had only model_info by 08:40:25. Therefore it never captured the target c4 decode workload.
- Nsys worker stdout/stderr and the report diagnostic database contain: `Common injection library initialized successfully`, OSRT injection initialized; then `CUDA profiling might have not been started correctly.` and `No CUDA events collected. Does the process use CUDA?`. Crucially, no `CUDA injection initialized successfully`, no CUPTI library loaded, and no CUDA activity/event count. The report exports only OSRT data and no CUDA API/kernel activity tables. This establishes that CUDA injection did not initialize in the actual V100 CUDA worker, not that the service did not execute CUDA.
- Although PID 3438632 owned 22,327,332,864 bytes of `injection_3438632_1000_storage.dat`, the stored stream was OSRT/process-tree session data, not CUDA activity (report confirms no CUDA tables/events). Total live session directory reached ~21 GiB under `/tmp/nvidia/nsight_systems/quadd_session_113438331`; `/tmp` fell from 22 GiB to 43 GiB free when only this confirmed stopped session's buffers were removed.
- Most probable causal mismatch: profiler launched the shell wrapper, which did `conda activate` then `exec python`; Python subsequently spawned SGLang multiprocessing workers. The report has no CUDA injection initialization in the child CUDA worker. The failure follows the CUDA workload child process, not the host-local V100 (minimal Nsys CUDA probe succeeds on that same device), driver/module state, or CUDA software-tracing capability. We did not isolate the exact low-level cause (e.g. exec/multiprocessing injection race vs process filter/injection restriction), so that remains an inference, not a proven specific defect.

## Installed Nsight CLI contract (queried locally)

- `nsys profile --help cuda`: graph granularity `graph` does not collect graph nodes and minimizes overhead; requires driver >=11.7 (installed driver 580.178.04 satisfies). `host-only` collects host-launched CUDA graphs. `node` can significantly increase runtime overhead. This makes graph-level host-only appropriate.
- `--capture-range` accepts `none`, `cudaProfilerApi`, `nvtx`, `hotkey`; the chosen `none` means no range gates collection. `--capture-range-end` applies only with capture-range and does not make `--duration` a disk-cap. `--stop-on-exit=true` applies to launched process exit only.
- `--sample=none`, `--cpuctxsw=none`, `--event-sample=none`, `--gpu-metrics-devices=none`, `--cuda-event-trace=false`, `--cuda-flush-interval=0` are supported on the installed CLI. `--trace=cuda,nvtx` is sufficient for requested CUDA+NVTX; no need for `osrt`.
- Nsight has no documented `NSYS_TMPDIR` flag. `TMPDIR` directs the temporary `.qdstrm`/report processing file but does not direct `/tmp/nvidia/nsight_systems` session `injection_*_storage.dat`. The observed staging location is the latter.

## Host-safe staging proof and current status

- Ordinary-user Nsight session shared staging can be isolated with a temporary bind mount of `/tmp/nvidia/nsight_systems` onto a dedicated loop-mounted ext4 filesystem. This is a real filesystem capacity limit, not a moved TMPDIR. A 4GB test filesystem was built at `/tmp/nsys-g016-quota-test.img`, mounted at `/mnt/nsys-g016-quota`, Nsys state directory permissions were made sticky-world-writable (`1777`) as required by the installed session manager, and bind-mounted over the actual staging path. The mount worked for short tests and was then unmounted; no residual mount/session exists. A minimal V100 Nsight probe using that actual bound path generated a 155,677-byte report and CUDA kernel summary (`g016_probe`, one kernel, ~450us). Session staging peaked at only ~36KB. This proves minimum-probe tracing and session staging capacity confinement when the correct Nsys session path is bound.
- Other smoke results using only `TMPDIR`/`NSYS_TMPDIR` did not relocate the session files, confirming those variables alone are not a disk bound. The loopfs staging mechanism is the relevant boundary. On capacity exhaustion, ext4 returns ENOSPC, which should stop storage growth at the configured limit; exhaustion behavior for a sustained capture has not been stress-tested because it could corrupt an in-progress report. Thus use short 1–2 s capture duration plus outer timeout/process cleanup; preserve free blocks for report finalization. A 4GB loopfs test left host `/tmp` and desktop tmpfs unchanged.
- Latest status: all Nsys/Falcon processes are stopped, the temporary bind and loop mounts are removed, V100 is idle (~7 MiB); RTX 2060 was never selected. `/mnt/data` has ~11GB free. No server-level Nsys retry has been made after the offline diagnosis.
