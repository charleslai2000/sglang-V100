# R17 direct-measurement differential notes

These notes support the next bounded empirical runs; they are not a substitute for the final report/matrix.

## 355-token FPM/PrefillStats difference: resolved

Using exact `.0` FPM capture `fpm-request-sidecar.jsonl` (2026-10-11), excluding the single health-check Extend:

- Sum of per-request `req.extend_input_len`: **75,021 tokens**.
- Sum of Forward `PrefillStats.log_input_tokens`: **75,376 tokens**.
- Capture log states V100 SM70 automatically selected `page_size=16`.
- Source `python/sglang/srt/managers/schedule_policy.py::_update_prefill_budget` explicitly applies `ceil_paged_tokens(extend_input_len)` before adding to `log_input_tokens`. `req.extend_input_len` remains the actual unrounded token payload length; page rounding is allocator/budget token accounting, not additional model input tokens.
- Recomputed per request as `ceil(extend_input_len / 16) * 16`, the payload-token sum rounds to **75,376**, exactly the aggregate PrefillStats field. Difference = **355 page-padding/budget tokens**, not extra model Forward computation.
- Distinctions for reporting: logical original input (sum unique user request input lengths), cached prefix reused, request scheduled extend payload, actual GPU payload `sum(len(r.fill_ids[len(prefix_indices):]))`, and page-aligned scheduler budget must be separate columns. In the measured radix-disabled capture cached tokens were zero. For non-chunked and the observed prefill batch construction, `extend_num_tokens` in `ScheduleBatch.prepare_for_extend` is the direct payload tensor length; scheduler snapshots are taken immediately before `model_runner.forward` and per-request `extend_input_len` is available. Do not divide page-aligned Stats by GPU time and call it actual computed input TPS.

## Existing request lifecycle timestamps: source support and limits

`ReqTimeStatsBase` / `SchedulerReqTimeStats` already record scheduler receive time, wait-queue entry, forward entry, prefill completion, first token ready and completion, all via `time.perf_counter`. TokenizerManager independently has API received/dispatch/first-token/finish/response-sent times and returns timestamp metadata in results. Request IDs exist in tokenizer state and `Req.rid`. G019's Chrome traces use CUPTI GPU timestamp coordinates and user annotations; the local G021 sidecar has FPM `forward_iter` and Forward request IDs but not this full chain. A production-boundary request-ID join is feasible with the accepted metrics flag `--enable-request-time-stats-logging` for logs, or existing profiler trace if request annotations survive. A new generic instrumentation framework is not required. Keep any new logging run clearly separate/instrumented; uninstrumented client service remains authority for throughput.

## NCU approach

The target-only root query succeeds for V100 UUID under `/usr/local/cuda/bin/ncu`; required SM/Tensor/DRAM/L2/stall counters exist in query inventory. GV100 full-Graph NCU has explicit `--graph-profiling graph`, `--replay-mode kernel`, `--launch-count`, `--launch-skip-before-match`, NVTX and CUDA profiler start/stop range filters. Existing SGLang `bench_one_batch` supports `--profile-activities CUDA_PROFILER`, a bounded `--profile-stage`, and fixed Decode step window; it also executes the real S1 ModelRunner and graph runner.

A first S1 bench attempt identified harness gaps, not production defects: (1) standalone `bench_one_batch.latency_test` initializes MoE but omits the existing `initialize_mamba_selective_state_update_backend(server_args)` call that Scheduler uses; (2) synthetic `Req` construction leaves `input_ids=None` in this fork/Falcon because scheduler's deferred H2D stage is absent; (3) production route runs with prebuilt SM70 MoE and dense Marlin runtime extensions. A temporary out-of-tree shim reused the existing Mamba initializer, corrected deterministic-token staging at the standalone boundary, and copied the already-built accepted runtime-only extensions into the clean G017 worktree after SHA equality checks (MoE `c64273b785dfc7854392170161f5e6d311be77a3cd5861b12a44144918beb172`; dense `b94235dac9713d28f8eee707b391f73bdec15b69317dc2e1fabd49329f763d09`). The S1 extension SHA remains `fea05241f2d588bf5a54f03a898360a49fbe0f256e25f59abbd9fd10b9257842`; no tracked SGLang source/math was changed.

A valid single-run smoke completed on 2026-10-12 against the pinned V100 with S1, 1K synthetic valid-vocabulary input, c1, 64 output steps, Graph keys [1,2,4], radix/piecewise disabled, static fraction .75. Standalone benchmark reported 3,595.75 prefill input tokens/s (0.28478s for 1,024 tokens) and median decode 32.48 output tokens/s (30.79ms/step). A bounded PyTorch profiler window recorded the EXTEND step at ~281.444ms CUDA total; eight Decode Graph steps had 246.441ms summed Self CUDA / 8 = 30.805ms per step. Trace files are `/mnt/data/pc01/sglang-v100-migration/profiles/r17-s1-valid_batch1_input1024_output64_{prefill,decode}.trace.json.gz`; raw benchmark output is `.../experiments/E026/r17-s1-valid.jsonl`. This is a **single c1 bench_one_batch diagnostic, not an uninstrumented service result**; synthetic inputs, warmup/cache and profiler scope differ from service matrix. The 1,024-token prefill throughput uses outer synchronized wall duration; the per-step profiler number is an overlapping operator attribution and must not be substituted for it. Decode excludes the first step via median and profile window selects steps 32–39. The target was idle after exit (7MiB, 0% GPU); MemAvailable 17.8GiB. No wider sweep or statistical claim is supported by this smoke.

The first Graph attempt did not delimit the intended workload; root NCU collected only an initialization kernel. The corrected capture uses NCU node profiling with an explicit NVTX start/end range (`torch.cuda.nvtx.range_start/end`, not push/pop), CUDA graph capture before the measured range, and exact kernel name filters. The range is contained in the primary ModelRunner process and includes the measured Prefill or Decode stage; NCU uses `--target-processes all` so helper/tokenizer descendants are tracked, but only the main worker matched selected kernels. For Prefill, selected kernels are actual CUTLASS MLP/attention and Mamba scan kernels from a real EXTEND call. For Decode, selected GPTQ GEMM/cublas GEMV/Mamba kernels occur during a captured Graph replay; their names and grids match the unprofiled Decode trace. The graph wrapper is not aggregated as one Graph metric because selecting individual nodes is more reliable in this path.

Formal per-kernel output is documented in the report and matrix. NCU produces repeat replay records for a selected kernel/grid; normalization script groups identical name/grid/block/device and averages the records. These are KERNEL_SCOPE readings, not sums/whole-Forward timing.
