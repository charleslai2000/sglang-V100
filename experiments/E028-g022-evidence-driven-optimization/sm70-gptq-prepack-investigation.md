Decisive incompatibilities, statically proven:
1. Real checkpoint is GPTQ-v1 Q4, group128, `sym=true`, `desc_act=true`, `static_groups=false`. SGLang `GPTQMarlinConfig.override_quantization_method` deliberately returns legacy GPTQ for desc_act on capability <8; explicit `quantization=gptq_marlin` raises. Current Falcon path is `GPTQLinearScheme -> GPTQLinearKernel(use_shuffle=False) -> gptq_gemm`; process-after-load wraps original tensors but does not reorder/duplicate them; every decode calls the Q4 no-shuffle GEMM. G017 is a separate explicit exact-c57 opt-in inside this same legacy kernel (`SGLANG_G017_Q4_FP32_CANDIDATE=1`, with exact extension path/SHA guards); S1 remains default. It is not Marlin and unchanged by the prepack question.
2. SM70 donor `csrc/quantization/marlin/marlin.cu::marlin_gemm` explicitly TORCH_CHECKs `g_idx_or_none` and `perm_or_none` are empty; error states “SM70 Marlin does not support act_order g_idx/perm.” Its GPTQ repack accepts a `perm`, but the dense GEMM doesn't. SGLang GPTQ Marlin preprocessing sorts `g_idx`, permutes/re-packs qweight and scales, but retains nonempty g_idx/perm for runtime activation permutation; `GPTQMarlinLinearKernel.apply -> apply_gptq_marlin_linear -> gptq_marlin_gemm` is thus incompatible even if the loader guard were bypassed. Repacking alone does not solve activation ordering.
3. The fixed FP32 accumulator oracle `abs(err) <= 1e-4 + 5e-5*abs(ref)` cannot be claimed satisfied by donor path: donor has no exposed pre-cast FP32 accumulator; it creates FP16 dequant fragments and FP16 output. Its design accumulates MMA into `float` (`sm70_marlin_gemm.cuh::ElementAccumulator`) then Volta epilogues/casts to half. Split-K uses per-CTA FP32 fragment accumulation but `Sm70AtomicFp16Epilogue` atomically accumulates FP16 partial outputs; direct path yields FP16. This is not equivalent evidence to the required pre-cast FP32 comparison. Static source establishes likely precision mismatch, but exact bad-element count against oracle has not been calculated; do not call the tolerance passed or failed. Minimal future discriminator only if a compatible kernel is developed: run one actual high-amplitude L43/down fixture with a test-only pre-cast FP32 output, compare FP64 mathematical GPTQ oracle (stored zero +1 and original activation order) at the frozen threshold. The existing oracle scripts are `experiments/E026-local-v100-s4-m3c/scripts/reconcile_candidate_numerics.py` and `diagnose_l43_down_strict.py`.

## Actual path, preprocessing and prepack design boundary

Checkpoint model: `config.json` quantization metadata is as above. 132 linear GPTQ tensors (44 layers × gate_proj/up_proj/down_proj), 88 K3072,N12288 matrices and 44 K12288,N3072 matrices. Loader creates original int32 qweight, packed int32 qzeros, FP16 scales and int32 `g_idx`; loader's per-module `process_weights_after_loading` invokes legacy wrapper but with `use_shuffle=False`, so it does not call `gptq_shuffle`, does not reorder weight rows, and leaves original g_idx. Every forward reshapes activation and calls `gptq_gemm(x,qweight,qzeros,scales,g_idx,false,4)`. This path decodes q/zero, reads scale by group and accumulates in FP32 chunks, then FP16 atomic partial reduction (see existing `sgl-kernel/csrc/gemm/gptq/gptq_kernel.cu`; e.g. `zeros[group,n]+1`, `dot22_8_h`, `atomicAdd`). It does not unpack/repack all weights each forward. Recurrent work is Q4 lane decode, g_idx->metadata indirection, zero+1, scaling, and each-K activation read/reduction; possible forward optimization is reducing metadata decode/indirection or input gathers via an act-order-aware packed layout, not relocating a full loader repack that is not present.

Existing Marlin GPTQ preprocessing `GPTQMarlinLinearKernel.process_weights_after_loading`: create ~80-SM workspace; sort g_idx and store permutation; unpack/repack qzeros; tile-repack packed qweight with permutation; permute scales; replace parameter storage. Forward apply calls `gptq_marlin_gemm` with activation, packed q, scale, zero, g_idx+perm and workspace. Donor dense SM70 GEMM rejects nonempty act-order metadata. Static groups false means the original group assignment to K is permuted; any act-order format must maintain `perm[j]=original K index at sorted position j`, transform weight row `Wq[perm[j],n]`, transform activation to `x'[j]=x[perm[j]]`, and apply scale/zero belonging to `g_idx[perm[j]]`. Ties/order must be deterministic and inverse metadata correct. For the Falcon MLP, gate_proj and up_proj have exactly equal g_idx and qzeros in layers 0/22/43, but their scales are different (true for all sampled layers); each output projection keeps separate scale and packed Q. Do not treat packed gate_up concat as one common scale object without concatenating both independent scale arrays along N. All 132 modules show qzeros stored value 7 for every nibble; GPTQ-v1 effective zero is therefore 8 here, but implementation must still preserve qzero+1 generically, not bake 8 from sym=true.

Reusable only: donor `gptq_marlin_repack.cu`’s 16x64 macro-tile Q4 bit/nibble reorder, scale permutation (`marlin_permute_scales`) and sorted-g_idx permutation concept. These are usable only after a new inference layout/kernel consumes sorted activations and matching group metadata; existing donor's standard 16x64 repacker output is not directly compatible with S1/G017's original layout or kernels. Alternative better first reuse is current mature S1 Q4 loader and implement a small metadata/reduction improvement in-place, preserving exact qweight/qzero/g_idx and one storage copy.

## Real tensor metadata, memory, and group consistency

CPU-only bounded audit script: `/mnt/data/pc01/sglang-v100-migration/experiments/G022/inspect_falcon_gptq_metadata.py`; output `falcon-gptq-metadata-audit.jsonl`. It did not instantiate CUDA or dequantize full weights. Whole checkpoint: 132 modules, 38,928,384 stored zero nibbles all 7 and therefore effective 8; 811,008 g_idx entries, of which 794,243 differ from simple K//128 ordering. Each g_idx has 128 entries/group and 24 groups at K3072 or 96 at K12288. Scales are FP16 finite. Gate/up g_idx and qzeros equal in audited layers 0/22/43; scales not equal.

`gptq_budget_and_mapping.py` with output `gptq-budget-and-gate-up-mapping.jsonl` gives exact source bytes and static predicted converted representation; script/hashes in artifact manifest to be finalized. Current 132 source matrices: qweights 2,491,416,576 B; qzeros 19,464,192 B; scales 77,856,768 B; g_idx 3,244,032 B; total 2,591,981,568 B (~2.414 GiB). Donor packed output bytes equal source Q4 qweight bytes (2,491,416,576); permuted FP16 scales 77,856,768 B; if zeros expanded as FP16 after qzero+1, another 77,856,768 B; sorted int32 g_idx another 3,244,032 B. Converted representation totals ~2,650,374,144 B (~2.468 GiB). If original is freed after conversion, weight-storage delta is +58,392,576 B (~55.7 MiB), plus workspace. If original/repack coexist throughout load, peak two-format layer data sum ~5,242,355,712 B (~4.883 GiB) for quant tensors alone; repack output+FP16 zero intermediate can overlap per layer, so ~2.569 GB extra at the largest gate/up module (static peak no other allocation). No full FP16 KxN weights are retained. Donor layer workspace from `marlin_make_workspace`: `SM_count * max_blocks_per_sm * int32`, default 80*1*4 = 320 B per module, 42,240 B total if each GPTQ linear kernel owns one workspace; runtime scratch may include additional temporary buffers below.

Donor runtime scratch has `a_tmp[M,K]` for act-order activation permutation (2*M*K bytes: K3072 is 6/12/24 KiB at M1/2/4; K12288 is 24/48/96 KiB), allocated every `gptq_marlin_gemm` call. `use_fp32_reduce=true` allocates `sms * min(ceil(M/16)*16,64) * 256 * 4`: for 80 SM and M1/M2/M4, the capped-at-64 factor is 16 for each, hence ~1.25 MiB per GEMM call at all three measured M values. The donor source shows a likely runtime bug for current semantics even beyond act-order: its `_sm70_marlin_v100_gemm_op` wrapper does not pass `is_zp_float=True`, while donor `marlin.cu` requires FP16 zero points for uint4 and rejects packed integer zero points. SGLang GPTQ Marlin preprocessing feeds packed/permuted integer GPTQ zero points and `apply_gptq_marlin_linear(...is_zp_float=False)`. Thus standard GPTQ-Marlin zero handling is also incompatible with the donor SM70 dense `uint4` branch; donor supports `uint4b8` only without runtime zeros, and its fixed-bias form cannot generically preserve arbitrary per-channel qzero+1. Need a transformed float-zp metadata path satisfying donor contract, and explain any precision rounding; merely registering op is not enough.

The current scheme's parameter replacement (`replace_parameter`) discards former tensor storage references; if conversion is done per layer in place and intermediates are released at each layer, the whole-model dual-format peak is not automatically 4.88 GiB; that figure is conservative all-modules simultaneous upper bound. However weights start loaded on target device in current loader and GPU headroom is low. To minimize peak: convert one layer at a time after transfer, materialize new packed Q and transformed scales/zero, atomically replace/remove old tensors after the new repack completes, retain only format needed by chosen route. Preserve original GPTQ checkpoint on disk/CPU for explicit rollback/reload. If a dual runtime route is required, do not permanently keep both GPU representations; conversion-on-demand incurs memory/copy and is outside present proposal. This is compatible with Prefill only if repack completes during load and old params can be released; otherwise fallback requires original Q tensors and duplicated storage.

## Next-stage proposal and acceptance
**Do not reuse donor SM70 dense GPTQMarlinLinearKernel as-is.** If implementing next, keep S1 and exact G017 Candidate unchanged, add a separate experimental act-order-aware prepack/kernel path only after agreeing on ownership. Minimal safe sequence:
1. New offline converter/helper creates per-module Q4 tile-packed weight with exact order vector `perm`, transformed FP16 scales and zero metadata; verify reconstruction of every selected code in FP64 against original q, qzeros+1, g_idx, scales, including actual arbitrary qzero support and the gate/up separate-scale concatenation. No full dense FP16 expansion.
2. Kernel consumes activation reordered `x[:,perm]`, uses zero values and group metadata consistent with GPTQ-v1, matches zero+scale decode, exposes FP32 accumulator before any cast. Differential test all six existing captured L0/L22/L43 gate_up/down fixtures and high-amplitude L43/down against frozen FP64→FP32 oracle; strict-bad must be zero with unchanged tolerance. Include M1/M2/M4 and request state/Graph replay.
3. Only then NCU one selected standalone kernel with safe root supervisor and original exact geometry, checking CTA/grid, duration, FP16 input/dequant, DRAM/L2, occupancy, issue, stalls; no broad Graph replay. A route that doesn't meet FP32 oracle is immediate no-go.
4. Actual production OFF/ON Graph forwards at c1/c2/c4 and stable admitted batch; observe real Graph node, QKV unaffected, actual selected path, memory. Then matched service matrices 1K/4K × c1/c2/c4, Prefill TPS, cold/warm TTFT and unchanged capacities; require true c4 GPU Forward and service Output TPS benefit. No default change without full acceptance.

**Bounded recommendation: NO-GO-DONOR**. Donor static packer is reusable source after layout/oracle inspection, but current SM70 dense kernel is disqualified by hard act-order rejection, incompatible packed GPTQ zero metadata and unexposed FP32 result boundary; cannot claim the frozen oracle. Implement an act-order+qzero-compatible consumer or smaller same-representation S1-path optimization next, not a dispatcher switch to donor. This is not a production performance judgment; no kernel/service certification was done.
