- Fixture identity is unchanged: all six immutable fixture manifests and x/qweight/qzeros/scales/g_idx hashes were rechecked against actual bytes. - Root cause of the 5/6→0/6 discrepancy: old `test_packed_candidate.py` invokes a distinct PyTorch extension `candidate-build/g017_q4_fp32_candidate.so` (SHA `300296a9…`) with `fp32_output=True`, yielding a `torch.float32` accumulator, then compares that value to the FP32 dequant/GEMM reference. The script calls this `y`/`b32` and casts it to float for comparison, but this is just a promoted FP16 value, not the pre-cast accumulator. Thus prior 5/6 was the FP32 accumulator gate; 0/6 is final FP16 output against an FP32 oracle. They are different values and different gates, not a mysterious same-path regression.
- Replayed the retained prototype binary with the original FP32 oracle: strict-bad counts are 0 on L0/down, L0/gate_up, L22/down, L22/gate_up, L43/gate_up, and 1 on L43/down, reproducing the historical 5/6. On a repeated candidate run the FP32 vs FP64-reference count is very close but not always bit-identical because different GEMM/reduction arithmetic shifts borderline elements; no tolerance changed.

For each element, the nearest possible IEEE FP16 value was selected and compared to the exact frozen limit.
