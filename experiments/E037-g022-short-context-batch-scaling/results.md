## INFERRED

- Runtime backend change is real at the actual eager Forward source-symbol boundary, and both GPU scheduling regime and GEMM implementation shift at M16. Independent Graph CUPTI replay vectors confirm a coincident activity change: Tensor-pipe elapsed-active rises from ≤2.12% at M1–8 to 9.81–11.04% at M16/32; DRAM `%peak` rises from ~29% to ~69–70%; reported raw read+write counter sums also jump at M16. The byte counters remain raw metric sums across replay and their normalization/scope is **unresolved**, so no GB/s calculation or claim that bytes/Forward increased by this exact ratio. The coordinated change is consistent with the confirmed reconstruct+Volta dense-GEMM path, but the counter evidence alone does not prove causation or identify memory bottleneck.
- Production Graph Event scaling is clear: step latency rises ~2.12× from M1 to M32 while aggregate tokens/s rises ~15.1×; amortized time/token falls 28.32→1.88ms. At M1–8, low tensor activity and only ~29–31% DRAM `%peak` coexist with ~76–82% SM Active, ~26–31% SM throughput and ~46% active-warp peak. This argues against a whole-forward HBM-saturated interpretation at low M; metrics are range averages and do not resolve a single bottleneck. The Eager trace confirms GPTQ alt4 remains a substantial repeated GPU family; Mamba activity scales with independent slot count, but neither is an exclusive wall owner.
- The only current owner bound derived from the Eager traces is interval-scoped: known kernel-family activity union covers 27.85–59.47ms of its corresponding 176.70–201.82ms instrumented Eager annotation; ~117–149ms remains outside classified GPU activity. Individual owner-interval unions overlap, so not additive; the analysis script additionally computes exclusivity only among same-trace GPU intervals, not an end-to-end CPU/Graph wall ledger. A matched E031 1K production Graph c4 trace has 84.75% GPU-activity-union / annotated-forward coverage, but a single c4/key4 trace cannot supply six-cell owner allocation. No trustworthy exclusive Graph owner budget exists yet.

- Calculated Mamba state per request from model dimensions and V100 dtypes: conv `[1,12800,3]` FP16 plus temporal `[1,24,128,256]` FP32 ×44 layers = 138,412,800 bytes (132 MiB) per slot. Independent b32 state alone is 4.125GiB before KV, 7.29GiB weights, graph/workspaces and runtime headroom. With Radix disabled, source sets max_mamba_cache_size=max_running_requests; with radix on and overlap extra_buffer, slot ratio is 5. This stage uses `--disable-radix-cache`, so that ratio is not the b32 limiter.
- **Historical error preserved; decision withdrawn (Owner ruling 2026-10-18):** The prior no-run rationale incorrectly equated host `MemAvailable` with GPU VRAM. These are independent resources; ≥8GiB applies only to host RAM. Subsequent GPU-qualified E037 runs establish feasibility through actual V100 NVML/CUDA observations; no theoretical aggregate-byte estimate substitutes for the measured allocation.
- S1 GPTQ dispatch follows the confirmed runtime boundary: native quantized alternate path through M8; reconstruction + Volta dense FP16 GEMM at M16/32. The exact Falcon `desc_act=true` configuration selects no-shuffle on SM70. Do not infer c57 M8+ route; c57 opt-in is guarded to M<=4 and larger batches use fallback.
